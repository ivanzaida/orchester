# Self-hosting an Orchester team server

A team server keeps a team's shared projects; its web admin, at `/admin`, sets up the server, its projects, people
and invites. It runs as two containers from Docker Hub, for linux/amd64 and linux/arm64:
`ivanzaida/orchester-server` and `ivanzaida/orchester-server-admin`. How the server works, its configuration and its
codes are in [docs/server-hosting.md](../../docs/server-hosting.md).

This repository is private, so self-hosters cannot download these files from GitHub. Their guide is the Docker Hub
page of both images, <https://hub.docker.com/r/ivanzaida/orchester-server>: `DOCKERHUB.md` with every compose file
and `.env.example` inlined, generated by `tools/dockerhub-description.ps1` ([Publishing a release](#publishing-a-release)).
This README is for the people who work on the repository.

## Quick start

On a Linux host with Docker and the compose plugin, a public DNS name with an `A` (and `AAAA`) record pointing to it,
and ports 80 and 443 reachable from the internet:

1. **Copy the two files** into a new folder (`mkdir orchester-server && cd orchester-server`): `compose.yaml` as it
   is, and `.env.example` as `.env`. They are in this folder at the release's tag (`server-v<version>`), attached to
   its GitHub Release (`.env.example` as `env.example`), and inline on the Docker Hub page.
2. **Fill in `.env`.** Set `ORCHESTER_VERSION` to the release (`0.1.1`), `ORCHESTER_HOST` to the DNS name, and
   `ORCHESTER_ADMIN_SECRET` to the output of `openssl rand -base64 32`. Every other value has a working default; the
   file explains each. Then `chmod 600 .env`.
3. **Start it:** `docker compose up -d`. Caddy gets the certificate for `ORCHESTER_HOST`. `docker compose ps` shows
   `server` and `admin` as *healthy* within a minute.
4. **Make the first admin.** `docker compose logs server` shows
   `Setup code: ABCD-EFGH (valid 24 hours; …)`. Open `https://<ORCHESTER_HOST>/admin`, enter the code, and choose the
   server's name and your username. Redeem it soon: anyone who can read the container's logs can use it until the
   server has an admin. `docker compose exec server orchester-server setup-code` makes a new one while it has none.

Then create a project in the admin and invite people from its *Invites*: with a code they enter in Orchester, or by
email once the server is linked to Orchester Cloud. Invites, codes too, are made only from an admin signed in with
two-factor authentication at Orchester Cloud, and only a person signed in with it accepts one or enters a code; the
admin says where to turn it on. Their Orchester joins the server at `https://<ORCHESTER_HOST>`.

The commands here are for `compose.yaml`; with another file, add `-f compose.private.yaml` or `-f compose.traefik.yaml`
to each `docker compose`.

## The files

| File | For |
| --- | --- |
| `compose.yaml` | A public DNS name: Caddy in front with a public certificate (the quick start). Ports 80, 443 and 443/udp |
| `compose.private.yaml` | No public DNS name, or air-gapped: the server presents its own certificate on port 8740 |
| `compose.traefik.yaml` | A host that already runs Traefik: labels, no published ports ([Behind Traefik](#behind-traefik)) |
| `.env.example` | Every variable of the three files, with how to choose or generate each value |
| `portainer-template.json` | The three files as Portainer app templates ([Portainer](#portainer)) |
| `compose.build.yaml` | Builds both images from this repository instead of pulling them (`docker compose -f compose.yaml -f compose.build.yaml up -d --build`) |
| `Dockerfile` | The server's image; the admin's is `web/Dockerfile.server` |

The server, the admin and Caddy (or Traefik) share a private network; the admin and the server's private API
listener (port 8741, which believes the admin's forwarded headers) are never published. `compose.yaml` and
`compose.private.yaml` rely on Docker keeping other containers out of that network, which Docker Engine on Linux does
by default; `compose.traefik.yaml` makes its network internal, so that holds there on any host. `compose.yaml` and
`compose.traefik.yaml` give that network the subnet `172.29.0.0/24`; if another network on the host has it, set
`ORCHESTER_SUBNET_PREFIX`.

Behind Caddy or Traefik the server signs the proxy's certificate into the key proof an app checks before it enters a
code. With `ORCHESTER_SERVER_PROXY_CERTIFICATE=auto` (the default) the server reads that certificate itself at
`https://<ORCHESTER_HOST>`, checked by the image's certificate authorities, so the proxy's renewals need nothing; a
fingerprint there instead must be set again after each renewal. `compose.yaml` maps `ORCHESTER_HOST` to Caddy for the
server (`extra_hosts`), so it reads on the stack's network. Until Caddy has its certificate, right after the first
start, the server's log may say once that it cannot read it; it reads again when an app asks. How it works and why it
is safe: [docs/server-hosting.md](../../docs/server-hosting.md), "The server admin".

## Orchester Cloud (optional)

With `ORCHESTER_ADMIN_CLOUD_URL` set (the default, `https://orchester-cloud.lurq.dev`), the admin offers *Link to
Orchester Cloud* at the end of the setup and in its *Settings*. Linking ties the server to its owner's Orchester Cloud
account: people then join with their cloud account, and invites go out by email (sent from an admin sign-in through
the cloud with two-factor authentication, accepted by a person with it). The browser carries everything
between the admin and the cloud; the server itself never connects to the cloud and verifies cloud identities offline.
The owner controls the link on the host at any time:

```sh
docker compose exec server orchester-server cloud show
docker compose exec server orchester-server cloud off     # stop accepting cloud identities; joined computers keep working
docker compose exec server orchester-server cloud on
docker compose exec server orchester-server cloud unlink
```

Without the cloud, leave `ORCHESTER_ADMIN_CLOUD_URL=` empty: setup stops after the first admin, people join with
codes, and admins sign in with a pairing code from their Orchester or an account code from the host
(`docker compose exec server orchester-server account-code <username>`).

## Air-gapped

Use `compose.private.yaml`; Caddy's public certificate needs the internet.

1. On a computer with the internet, fetch the images and the files, and save the images to one archive:

   ```sh
   docker pull ivanzaida/orchester-server:0.1.1
   docker pull ivanzaida/orchester-server-admin:0.1.1
   docker save -o orchester-server-0.1.1.tar ivanzaida/orchester-server:0.1.1 ivanzaida/orchester-server-admin:0.1.1
   ```

   For an arm64 host, add `--platform linux/arm64` to both `docker pull`s.
2. Carry `orchester-server-0.1.1.tar`, `compose.private.yaml` and `.env.example` to the host, and run
   `docker load -i orchester-server-0.1.1.tar` there.
3. In `.env` (from `.env.example`): `ORCHESTER_VERSION=0.1.1`, `ORCHESTER_ADMIN_SECRET`, `ORCHESTER_ADMIN_CLOUD_URL=`
   (empty), and `ORCHESTER_SERVER_TLS_NAMES` with the names and addresses people reach the host by. The names are read
   only when the server makes its certificate, on its first start.
4. `docker compose -f compose.private.yaml up -d`, then `docker compose -f compose.private.yaml logs server` for the
   setup code and the certificate's check code. Open `https://<host>:8740/admin`. The browser warns about the
   certificate: compare the SHA-256 it shows with the one from
   `docker compose -f compose.private.yaml exec server orchester-server tls show` before you trust it.

Nothing is fetched at run time. People's Orchester pins the server's certificate when they join with a code; they
compare its check code once.

Codes and invites need two-factor authentication the server can check: pin Orchester Cloud's root once,
`docker compose -f compose.private.yaml exec server orchester-server cloud pin <root public key>`, without linking.
People's Orchester then reaches the cloud once per code; the server never does. Without a pinned root the server takes
only its setup code ([docs/server-hosting.md](../../docs/server-hosting.md), "Air-gapped").

## Upgrades

1. Take a backup (below).
2. Set `ORCHESTER_VERSION` in `.env` to the new release, then:

   ```sh
   docker compose pull
   docker compose up -d
   ```

   The server migrates its database when it starts. The migrations are forward-only: to go back to an older release,
   restore the backup taken before the upgrade and set the old version.

The release notes on GitHub list what changed. `latest` follows every release; pin a version instead, so an upgrade
happens only when you change it.

## Backups

The `server_data` volume holds the database, and with `compose.private.yaml` the server's certificate. Take an online
snapshot while the server runs, with a new file name each time:

```sh
docker compose exec server mkdir -p /data/backups
docker compose exec server orchester-server backup /data/backups/orchester-server-$(date +%F).db
docker compose cp server:/data/backups/orchester-server-$(date +%F).db .
# compose.private.yaml only: the certificate, or every computer confirms a new one after a restore
docker compose -f compose.private.yaml cp server:/data/tls ./tls
```

Keep the snapshots as carefully as the server: they hold its keys, its codes' HMACs and the device tokens' digests.
Keep `.env` with them. `docker compose down` keeps the volumes; `docker compose down -v` deletes them.

To restore one, stop the server, copy it in (the database it replaces, with its `-wal` and `-shm` files, moves to
`/data/before-restore`), and start again. For `compose.private.yaml`, add `-f compose.private.yaml` and
`-v "$PWD/tls:/restore-tls:ro"` to bring the certificate back too:

```sh
docker compose stop server
docker compose run --rm --no-deps --user root -v "$PWD/orchester-server-2026-10-16.db:/restore.db:ro" \
  --entrypoint sh server -c 'mkdir -p /data/before-restore && for f in /data/orchester-server.db* /data/tls; do
    [ -e "$f" ] && mv "$f" /data/before-restore/; done; [ ! -d /restore-tls ] || cp -r /restore-tls /data/tls;
    cp /restore.db /data/orchester-server.db && chown -R 10001:10001 /data'
docker compose up -d
```

It runs as root because a snapshot copied out with `docker compose cp` belongs to the host's user, then gives `/data`
back to the server's uid 10001. More in [docs/server-hosting.md](../../docs/server-hosting.md), "Backups".

## Behind Traefik

`compose.traefik.yaml` puts the server behind a Traefik (v2 or v3, with its Docker provider) that already holds ports
80 and 443. Traefik sends every path on `ORCHESTER_HOST` to the server, sends `Strict-Transport-Security`, and
redirects plain HTTP to HTTPS.

1. Look up, in Traefik's own configuration: its network (default `traefik`), its HTTPS and HTTP entry points
   (`websecure`, `web`) and its certificate resolver (`letsencrypt`). Set `TRAEFIK_NETWORK`, `TRAEFIK_ENTRYPOINT`,
   `TRAEFIK_HTTP_ENTRYPOINT` and `TRAEFIK_CERT_RESOLVER` if they differ.
2. Set `TRAEFIK_ADDRESS` to Traefik's address on that network, without the `/16`:

   ```sh
   docker network inspect traefik --format '{{range .Containers}}{{.Name}} {{.IPv4Address}}{{println}}{{end}}'
   ```

   The server believes a forwarded client address (for its limits on failed joins) only from there. With a `/16`
   it would believe every container on Traefik's network. If Traefik's container is recreated, it may get another
   address: check it after every Traefik upgrade, or give Traefik a fixed address in its own setup.
3. Set `ORCHESTER_HOST`, `ORCHESTER_VERSION` and `ORCHESTER_ADMIN_SECRET`, then
   `docker compose -f compose.traefik.yaml up -d` and `docker compose -f compose.traefik.yaml logs server` for the
   setup code.

Only the server joins Traefik's network. Its own network is internal, so the admin has no route out: invites by email
are carried to Orchester Cloud by the inviter's browser instead of the admin. The server reads Traefik's certificate
(`auto`) at `https://<ORCHESTER_HOST>` through Traefik's network, which has a route out: the host must reach its own
public name (hairpin NAT). If it cannot, and Traefik's HTTPS entry point listens on 443 in its container, give the
server `extra_hosts: ["<ORCHESTER_HOST>:<TRAEFIK_ADDRESS>"]`, or set the fingerprint instead. The server's log says
when it cannot read it, and apps then enter no codes. The admin's paths carry no codes or
tokens, so Traefik's access log needs nothing special for this host.

## Portainer

`portainer-template.json` holds the three compose files as app templates (*Orchester team server*, *… (private
network)*, *… (Traefik)*), each asking for its variables. Portainer reads templates from a URL: put the file where your
Portainer can fetch it, then *Settings* → *App Templates* → its URL. Or paste a compose file into *Stacks* → *Add
stack* → *Web editor* with the variables of `.env.example`. After the deploy, the `server` container's log has the
setup code.

## Publishing a release

For the maintainers. `.github/workflows/server-release.yml` runs on a `server-v<version>` tag whose version is the
workspace's (`Cargo.toml`): it builds both images for amd64 and arm64, pushes them to Docker Hub (`<version>`, and
`<major>.<minor>` and `latest` unless it is a pre-release such as `-rc.1`), and creates the GitHub Release with the
digests and these files. It needs the secrets `DOCKERHUB_USERNAME` and `DOCKERHUB_TOKEN` (an access token with Read &
Write) and the variable `DOCKERHUB_NAMESPACE`.

**The Docker Hub page** is the self-hosters' whole guide. `DOCKERHUB.md` is its text; each line
`<!-- inline: <file> -->` becomes that file of this folder, byte for byte, in a code block, so the page cannot drift
from the files. Build it with `powershell -File tools/dockerhub-description.ps1` (it writes
`.tmp/dockerhub/description.md` and fails beyond Docker Hub's 25,000 characters). After a release that is not a
pre-release, the workflow publishes the page and a short description to both image repositories when the secret
`DOCKERHUB_DESCRIPTION_TOKEN` (an access token with Read, Write & Delete) is set; otherwise it skips them with a
notice. *Run workflow* with *description_only* refreshes only the page, from any branch. Every run keeps the page as
its artifact `dockerhub-description`, to paste into both repositories by hand (*Repository* → *Edit* the overview).

The release refuses a `portainer-template.json` whose compose files differ from the ones here. After changing a
compose file, update its template, for example:

```sh
jq --rawfile f compose.traefik.yaml '(.templates[] | select(.note | contains("compose.traefik.yaml")) | .stackFile) = $f' \
  portainer-template.json > portainer-template.json.new && mv portainer-template.json.new portainer-template.json
```
