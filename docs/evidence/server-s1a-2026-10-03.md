# S1a server and accounts — implementation and validation

2026-10-03. Branch `codex/server-s1a`, worktree `.tmp/worktrees/codex-server-s1a`, created from `master` at
`242094bb95fe54998be3d782565e4e1f8714f38b`. Changes on this branch are unmerged. The user's independent review
first reported PASS with findings (one major and eight minors). The second independent review of `9a2a8f47`
verified those fixes, then reported FAIL on concurrent password-change limiting plus four minors. The third review
of `ea799449..499840a9` verified the second review fixes except a regression: Caddy clients shared the new 64-peer
connection budget. This follow-up fixes that major and the third review's minors and awaits independent re-review.
The updated specification supplied during implementation confirms the proposed decisions; its S1a requirements
match the worktree's specification.

S1a implementation includes the types-only `orchester-api`, `orchester-server`, typed user/session ids in core,
versioned SQLite WAL storage, accounts, session authentication/revocation, host bootstrap/recovery commands,
Argon2id password hashing, SHA-256-only token storage, rate limiting, trusted proxy address handling, append-only
audit records, optional PEM TLS, and redacted request logs and error responses. Requests on every route are bounded
to 1 MiB. Initial-password sessions can change their password or sign out; user changes are rechecked in write
transactions so revocation, reset and last-admin protection remain effective during concurrent requests.

New direct third-party dependencies are the specification's `axum`, `argon2`, `tokio-rustls`, `hyper` and `hyper-util`.
The latter two expose the HTTP connection builder and Tokio IO/timer/axum service adapter requested in review m1;
they were already transitive dependencies. The dependency table and `[workspace.dependencies]` record their reasons.
Existing rusqlite gains only its `backup` feature for review m8. Salt, password and token randomness uses
Argon2's re-exported OS RNG (backed by getrandom); no separate
randomness dependency or HTTP client was added. Other dependencies were already in the workspace.
The API credential wipes its memory using existing `zeroize`; it accepts whitespace passwords, since core's
project-secret type rejects them but the server password specification has no composition rules.

No desktop/UI, task-store, project, claim, event-stream or run-status changes are part of this phase.
Docker/Caddy configuration and operating instructions are in `deploy/server/` and `docs/server-hosting.md`.

## First independent review fixes (verified by the second review)

| Finding | Change and regression coverage |
| --- | --- |
| M1 | Every `X-Forwarded-For` line is consumed in order as one comma list. The whole list is validated, then walked from the right through trusted hops; malformed lists use the peer. Rotating forged first lines no longer bypass the 20-failure address block; multiple-line and comma-list tests cover it. |
| m1 | Hyper with TokioTimer gives headers and keep-alive idle connections a 10-second deadline. Body reads have an absolute 10-second deadline, including continued slow input. HTTP connections are capped at 256; existing TLS handshakes remain capped at 64/10 seconds; shutdown drains for at most 15 seconds. Real TCP/TLS tests observe closure and a body `408`. |
| m2 | Trusted proxy entries accept IPv4/IPv6 CIDRs and exact IPs. Mapped IPv4 is canonicalized, forwarding hops accept ports/brackets, and IPv6 address counters use /64. Tests cover matching, malformed inputs and distinct/same IPv6 networks. |
| m3 | Password changes have a separate per-user 5-failure/15-minute counter checked before hashing acquisition. Failures append `password_change_failed` with user ids and address. Tests use multiple sessions, another user, Retry-After/clock expiry, and a malformed stored hash to prove blocked requests skip verification. Sign-in remains usable during the password-change block. |
| m4 | Authentication uses a read connection until last use moves by more than a minute; refresh rechecks authorization in the write transaction. A test holds a competing writer and confirms ordinary authentication still succeeds, then checks refresh and the exact 30-day persisted boundary. |
| m5 | Oversized bodies return `413 payload_too_large`, including chunked requests; unsupported methods return `405 method_not_allowed`. Both are documented as common API errors and covered by HTTP tests. |
| m6 | All four JSON request records reject unknown fields with `400 bad_request`. User changes that leave stored values unchanged return the user without mutation or audit. Tests verify rejection is atomic and no-op audit counts stay unchanged. |
| m7 | Internal errors log their variant and safe SQLite primary/extended codes or IO kind/OS code. Raw source messages, SQL/request values and filenames are withheld; Debug is also redacted. A trigger puts a token in a SQLite failure source; HTTP, Debug and captured logs omit it while logs retain diagnostic codes. |
| m8 | `orchester-server backup <path>` makes a consistent online snapshot, refuses existing paths and removes a failed new snapshot. The CLI test checks live WAL contents, integrity, restore/sign-in, and overwrite/source protection. The documented Docker backup/copy procedure verifies snapshot data and mode 0600 on a native data volume. |

## Second independent review fixes (third review verified all except the proxy-cap regression)

| Finding | Change and regression coverage |
| --- | --- |
| Major | Password changes reserve per-user capacity atomically before entering the hashing queue; failures plus in-flight attempts cannot exceed five. The block is rechecked immediately after acquiring a hashing permit. A 40-request wrong-password burst returns exactly five `401`s and 35 `429`s, with five failure audit rows; expiry and independent sign-in remain covered. |
| m-a | HTTP connections retain the global 256 cap and gain a 64-per-peer cap; TLS handshakes retain the global 64 cap and gain an 8-per-peer cap. Excess sockets close immediately, so an idle peer cannot queue other peers behind its sockets. A two-second first-byte deadline applies before TLS and before HTTP; existing ten-second handshake/header/keep-alive/body deadlines remain. Real socket tests open 300 idle TCP or 70 silent TLS connections from one loopback address and obtain a response from another within one second, then observe silent connections closing within three seconds. |
| m-b | Sign-in reserves username and address capacity before hashing, using the same guard as password changes and retaining the 5/20 failure rules. Concurrent bursts exercise both budgets. A malformed stored hash makes verification observable as `500`; only five admitted requests reach it, while the other 35 return `429`. Sequential successful checks release reservations, including a valid current password followed by an invalid new password. Guards release cancelled pre-hash reservations; a guard moved into a started blocking worker remains charged if its result is abandoned. |
| m-c | Hosting instructions warn that trusted IPs/CIDRs must never contain client addresses, since those clients could forge forwarding hops. |
| m-d | Backup copies the whole database with one SQLite backup step under a read snapshot. Commits cannot restart the copy; busy/locked incomplete steps return a typed error and remove the new output file. A test continuously commits WAL updates while copying an 8 MiB database, requires completion within five seconds, and checks snapshot integrity, payload and counter consistency. |

No additional dependency, desktop/UI change or S1b work was added for these follow-ups.

## Third independent review fixes

| Finding | Change and regression coverage |
| --- | --- |
| Major | HTTP and TLS peer caps exempt connections whose actual IP matches `trusted_proxies`; trusted connections still consume global capacity and retain every read deadline. Trust matching precedes IPv6 /64 grouping, and trusted leases do not consume neighbouring untrusted clients' group budget. With 64 incomplete forwarded-client bodies, a 65th trusted-proxy request returns `200` within one second; a simultaneous untrusted peer remains capped at 64. Further tests verify the 256 global HTTP cap and trusted TLS proxy exemption beyond 64 HTTP connections and 32 handshakes, while retaining the 64 global handshake cap. Exact, CIDR and mapped IPv4 proxy entries are exercised. |
| m1 | CLI backup opens an existing source with SQLite read-only flags and never opens `Server`, requests a migration write transaction, creates a source database or changes journal mode. The continuous-commit 8 MiB backup test now runs the actual CLI. A deterministic test holds an IMMEDIATE WAL writer with an uncommitted schema change and gets a consistent committed snapshot within two seconds. Missing-source and future-schema physical snapshot tests verify no creation or migration. Host user commands retain their five-second busy timeout; busy/locked diagnostics clearly say to retry after the writer releases the lock. Create/reset tests hold a writer, require failure within a deadline, and verify the retry message and empty credential stdout. |
| m2 | The fixed per-untrusted-peer handshake cap increases from 8 to 32, retaining the 64 global cap. A real TLS test admits the 32nd handshake while 31 are pending, immediately closes the 33rd, then completes all 32 admitted handshakes. The hosting instructions record the fixed choice. |
| m3 | Hosting instructions document the username's 5-failure/15-minute sign-in lockout, absence of a dedicated admin unlock, and that password reset does not clear the running server's counters. Waiting for Retry-After expires the lock; a server restart clears all in-memory rate limits. No additional admin endpoint was introduced for this note. |

All server tests start a real loopback server with a disposable data directory under the worktree's `.tmp/server-s1a/tests` and an
explicit settable clock. They cover bootstrap; initial password restrictions and sign-out; host reset; session list,
own-session revoke and cross-user refusal; password change and other-session revocation; the exact idle-expiry
boundary and fresh sign-in; character limits; persistence, WAL and schema rejection; every admin endpoint; disabled
users and last-admin protection under concurrent demotions; username/address limits with Retry-After and clock
advance; unknown-user password verification timing; trusted and untrusted forwarded addresses; token format/hash
storage; PHC parameters; TLS against a disposable test CA; one-time CLI output; TOML/environment configuration;
request size/error handling; no CORS; secret-free Debug, errors and captured logs; and append-only audit records.

The initial log-capture test used a thread-local subscriber that did not capture the server tasks; using a global
test capture corrected that failure. Test functions were split to satisfy the 80-line gate. These corrections are
included in the passing final suite.

The first Linux review-fix run passed 29 tests and failed a Unix-mode assertion: WSL's Windows-mounted test directory
reports mode 0777 even for files created with mode 0600. The portable backup test now checks snapshot integrity and
restore; mode 0600 is verified separately on Docker's native Linux data volume.

Docker validation used the shipped Dockerfile, Compose services and Caddyfile. The test override changed only the
published ports to dynamic loopback ports; `ORCHESTER_HOST=localhost` selected Caddy's local CA. The public CA
certificate was copied to the scratch directory for HTTPS verification. Host CLI passwords and bearer tokens
stayed in the smoke test's memory and were checked against captured server logs without printing them.
Docker was initially unavailable, then the user started its engine and image build/start/HTTPS passed. It was available
for all three review follow-ups and their rebuilt image/start/HTTPS checks passed; the earlier unavailable-engine statement
is no longer current. First-review output is in
`.tmp/server-s1a/review-{check,windows-tests,linux-tests,macos-check,docker-build,docker-start,docker-smoke}.log`.
